Task1 — P0: Setup — Sec 3: Runtime & Tooling

Purpose of this file:
Explain each Sec 3 component before installation — what it is, how it works
(Windows now, Linux later for hosting), its function, what breaks without it,
and how the components chain together at runtime.

─────────────────────────────────────────────────────────────────────────
3.1 Node.js LTS + npm
─────────────────────────────────────────────────────────────────────────

WHAT IT IS
- Node.js: a JavaScript runtime. It takes the V8 engine (from Chrome) and
  runs JS outside the browser — i.e., on your machine or a server.
- npm (Node Package Manager): ships bundled with Node. It installs, updates,
  and manages third-party JS libraries (Express, React, Mongoose, etc.)
  from the npm registry.

HOW IT WORKS
- You write JS in .js files. Node reads and executes them via its event loop
  (single-threaded, non-blocking I/O). It exposes APIs the browser doesn't:
  file system (fs), network (http, net), OS, streams, child processes.
- npm resolves dependencies from package.json, downloads them into
  node_modules/, and locks exact versions in package-lock.json.

WINDOWS INTERACTION
- Installs as a system binary: node.exe + npm.cmd, added to PATH.
- VSCode terminal (PowerShell/CMD) can call `node` and `npm` directly.
- node_modules/ can get huge and deeply nested — Windows path-length limit
  (260 chars) can occasionally bite; keep project paths short.

LINUX INTERACTION (later, on host)
- Installed via nvm (recommended) or apt. Same runtime, same commands.
- On servers (Render/Railway), Node is provisioned by the platform from
  the `engines.node` field in package.json or a .nvmrc file.
- Difference: case-sensitive filesystem, forward slashes, no .exe.

FUNCTIONS
- Execute backend JS (Express server, Socket.io, scripts, build tools).
- Provide the npm CLI for dependency + script management.

WITHOUT IT
- No backend runtime. No Express server. No React/Vite build.
- Nothing in the MERN stack runs. This is the foundation.

CHAIN POSITION
- First link: everything downstream (npm installs, Vite, Express) depends on it.

─────────────────────────────────────────────────────────────────────────
3.2 MongoDB Atlas (cloud) or local MongoDB
─────────────────────────────────────────────────────────────────────────

WHAT IT IS
- MongoDB: a NoSQL database. Stores data as flexible JSON-like documents
  inside collections, instead of rows/tables.
- Atlas: MongoDB's managed cloud service — they run the DB, you get a URI.
- Local MongoDB: the same engine running on your own machine.

HOW IT WORKS
- A mongod process listens on a port (default 27017).
- Clients (your backend via Mongoose) connect over TCP using a connection
  string (mongodb:// or mongodb+srv://).
- Data is stored in BSON (binary JSON) files on disk; queries use
  find/insert/update/delete with a rich query language.

WINDOWS INTERACTION
- Local: install MongoDB Community Server as a Windows service; it starts
  with the OS. Connect via mongodb://localhost:27017.
- Atlas: no local install — you just get a URI and connect over the internet.
- MongoDB Compass (GUI) or the VSCode MongoDB extension can browse data.

LINUX INTERACTION (later, on host)
- Preferred: Atlas (no server maintenance, backups, scaling handled).
- If self-hosting later: run mongod as a systemd service, behind auth +
  firewall. You'd need to manage backups, TLS, and access control yourself.

FUNCTIONS
- Persist all app state: users, tasks, bids, bookings, payments,
  reviews, messages.
- Serve reads/writes to the backend (never the frontend directly).

WITHOUT IT
- No persistence. Backend could still run, but every restart wipes data.
- No accounts, no tasks, no bookings — the app is stateless and useless.

CHAIN POSITION
- Second link: the backend (Express) needs a DB to persist into.
- Recommendation: start with Atlas Free (M0) — zero setup, works from
  both Windows and Linux, and matches production shape from day one.

─────────────────────────────────────────────────────────────────────────
3.3 API Testing Tool — Postman or Thunder Client
─────────────────────────────────────────────────────────────────────────

WHAT IT IS
- A GUI client for sending HTTP requests to your backend and inspecting
  responses — without needing a frontend.
- Postman: standalone cross-platform app, feature-rich, heavy.
- Thunder Client: VSCode extension, lightweight, lives in your editor.

HOW IT WORKS
- You craft a request: method (GET/POST/PATCH/DELETE), URL, headers
  (e.g., Authorization: Bearer <JWT>), body (JSON).
- It sends the request to your running Express server and shows:
  status code, response headers, response body, timing.
- You can save requests into collections, use environment variables
  (e.g., {{baseUrl}}, {{token}}), and chain them.

WINDOWS INTERACTION
- Postman: install as a Windows app, signs into a cloud account for sync.
- Thunder Client: install from VSCode marketplace; runs in-editor.

LINUX INTERACTION (later, on host)
- Not needed on the server — it's a dev-time tool on your machine.
- If you host on Linux later, the equivalent of "testing in prod" would be
  curl or httpie from the shell, not Postman.

FUNCTIONS
- Verify each endpoint independently of the UI.
- Debug auth flows (test JWT issuance/validation without React).
- Test webhooks (Stripe) locally by pointing Stripe CLI at your endpoint.
- Build a repeatable collection that acts as API documentation.

WITHOUT IT
- You'd test by writing throwaway scripts or curl commands — slower,
  no saved history, no env variables, harder to iterate.
- Harder to isolate: is the bug in the frontend, backend, or DB?

CHAIN POSITION
- Third link: sits beside the backend as a client. Once Node + MongoDB
  are up and the backend runs, this is how you talk to it before React exists.

─────────────────────────────────────────────────────────────────────────
RUNTIME SEQUENCE — how 3.1 → 3.2 → 3.3 chain
─────────────────────────────────────────────────────────────────────────

1. Node.js (3.1) is installed → provides the runtime.
2. `npm init` + `npm install express mongoose ...` (later in P0/Sec 5)
   → npm downloads deps into backend/node_modules/.
3. MongoDB Atlas (3.2) is provisioned → you copy a connection URI.
4. Backend code reads MONGO_URI from .env → Mongoose connects to Atlas
   → mongod on Atlas accepts the TCP connection.
5. `node server.js` (or nodemon) starts Express → listens on PORT.
6. You open Postman/Thunder Client (3.3) → send a test request
   (e.g., POST /auth/register) → backend validates → writes to MongoDB
   → returns JSON → you see it in the tool.
7. Later, when React is added, the frontend replaces the testing tool
   as the main client — but Postman/Thunder Client stay for debugging.

─────────────────────────────────────────────────────────────────────────
ADDENDUM — Clarification: Node.js is a runtime, not a compiler
─────────────────────────────────────────────────────────────────────────

CORRECTION TO 3.1 MENTAL MODEL

Common misconception:
  "Node.js is the compiler that makes JS work on the whole machine."

Correct model:
  Node.js is a RUNTIME — an interpreter + environment that executes
  JavaScript outside the browser, exposing OS-level APIs.

─────────────────────────────────────────────────────────────────────────
RUNTIME vs COMPILER
─────────────────────────────────────────────────────────────────────────
- Compiler: translates source code (e.g., C) into machine code ahead of
  time (AOT). Output is a binary. Runs natively.
- Interpreter: reads source and executes it directly, no separate build step.
- Runtime: the whole execution environment — interpreter + standard library
  + global APIs + memory management + event loop.

Node = runtime.
  - Uses V8 (same engine as Chrome) as its JS engine.
  - V8 does JIT (Just-In-Time) compilation internally — compiles hot code
    paths to machine code at runtime for speed.
  - So compilation *happens*, but it is an internal detail of V8.
    Node itself is the wrapper: event loop + OS bindings + module system.

─────────────────────────────────────────────────────────────────────────
"SAME LANGUAGE, DIFFERENT ENVIRONMENT"
─────────────────────────────────────────────────────────────────────────
JS in the browser:
  - Globals: window, document, fetch, localStorage, alert.
  - Cannot read files, open sockets, or spawn processes.
  - Sandboxed for user safety.

JS in Node:
  - Globals: process, __dirname, global, Buffer, module, require.
  - APIs: fs (files), http/net (sockets), os (system), child_process.
  - No DOM, no window — those are browser concepts.

The LANGUAGE (syntax, types, functions) is the same.
The ENVIRONMENT (what APIs exist, what the code can touch) differs.

─────────────────────────────────────────────────────────────────────────
"THE WHOLE MACHINE" — precise phrasing
─────────────────────────────────────────────────────────────────────────
- Node does NOT "make the machine its environment."
- Node is a PROCESS running ON the machine, under the OS.
- It can *access* machine resources (files, ports, processes) via its APIs,
  but only within the permissions the OS grants that process.
- Same as any program: sandboxed by user privileges, firewall, filesystem
  permissions.

Analogy:
  Node is a tenant in an apartment (the OS). It can use the utilities
  (water = files, electricity = network) that the landlord (OS) allows.
  It doesn't own the building.

─────────────────────────────────────────────────────────────────────────
TIGHT SUMMARY
─────────────────────────────────────────────────────────────────────────
Node = JS runtime.
  - Executes JS outside the browser.
  - Exposes OS-level APIs instead of browser APIs.
  - Uses V8 under the hood (which JIT-compiles hot paths).
  - Runs as a single process, subject to OS permissions — not the machine.

Carry this model forward: whenever you hear "Node," think
"runtime with OS-level powers, sandboxed like any process."
